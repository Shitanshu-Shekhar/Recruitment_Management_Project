Product Requirements Document: Recruitment Management System (MERN)
Derived from the Mechatron Lab industrial training report. Written so it can be handed directly to an AI coding agent (such as Antigravity) to generate the full project.
1. Overview
Product name: Recruitment Management System (RMS)
One-line summary: A full-stack web application where recruiters post jobs and manage applicants, applicants build profiles, upload resumes and apply for jobs, and admins oversee the platform.
Problem: Small and medium organizations manage hiring with emails, spreadsheets and paper records. This causes delayed hiring, poor candidate tracking, duplicate data and weak communication.
Solution: A lightweight, secure, centralized platform covering the complete hiring workflow: job posting, applications, resume storage, status tracking and role-based dashboards.
Tech stack (fixed):
Frontend: React.js (Vite), Tailwind CSS, React Router, Axios, Context API for auth
Backend: Node.js, Express.js (monolithic REST API)
Database: MongoDB with Mongoose
Auth: JWT and bcrypt, with role-based access control
File uploads: Multer (resumes stored on server disk)
Tools: Git/GitHub, Postman, MongoDB Compass
2. Goals and Non-Goals
Goals
Responsive web app that works on desktop, tablet and mobile.
Secure registration, login, logout and protected routes.
Separate recruiter, applicant and admin dashboards.
Full CRUD for job postings; job applications with status tracking.
Resume upload with file type and size validation.
Secure handling of candidate data (hashed passwords, validated uploads, rejected unauthorized access).

4. Core User Flows
Auth flow: User → Login → Express API (bcrypt credential check) → JWT issued → Role verification → Recruiter / Applicant / Admin dashboard → REST API → MongoDB → Logout
Recruiter flow:
Register or log in as a recruiter.
Open Recruiter Dashboard and click Post New Job.
Enter title, description, location, job type, required skills, deadline; publish.
Open a job to view submitted applications and resumes.
Update each application status: Applied → Under Review → Shortlisted → Selected / Rejected.
Applicant flow:
Register or log in as an applicant and complete the profile.
Upload a resume (PDF, DOC or DOCX).
Browse or search jobs and open a job to view details.
Click Apply (with optional cover letter).
Track the status of every application from the Applicant Dashboard.
5. Functional Requirements
5.1 Authentication and Authorization (FR-AUTH)
FR-AUTH-1: Register with name, email, password, role (applicant or recruiter). Email must be unique.
FR-AUTH-2: Passwords hashed with bcrypt (salt rounds 10 or more). Never return the hash in any API response.
FR-AUTH-3: Login with email and password; return a signed JWT (expiry 1 day) plus basic user info.
FR-AUTH-4: Logout clears the token on the client (stateless JWT).
FR-AUTH-5: protect middleware verifies the JWT; invalid or expired tokens return 401.
FR-AUTH-6: authorizeRoles(...roles) middleware returns 403 for wrong roles.
FR-AUTH-7: Frontend ProtectedRoute component redirects unauthenticated users to login and wrong-role users to their own dashboard.
FR-AUTH-8: Deactivated users (admin action) cannot log in.
5.2 Job Management (FR-JOB)
FR-JOB-1: Recruiters create jobs: title, description, location, jobType (Full-time, Part-time, Internship, Contract, Remote), skills[], deadline, status (Open or Closed).
FR-JOB-2: Recruiters edit, delete or close only their own jobs (ownership check).
FR-JOB-3: Public/applicant job listing with pagination (default 10 per page).
FR-JOB-4: Search by keyword (title, description, skills) and filter by location, jobType and status.
FR-JOB-5: Job detail page showing full job info and an Apply button for applicants.
FR-JOB-6: Jobs past their deadline are shown as closed and cannot receive new applications.
FR-JOB-7: Recruiter dashboard lists own jobs with applicant counts.
5.3 Candidate Profile Management (FR-PROF)
FR-PROF-1: Each applicant has one profile (1:1 with user): phone, education, skills[], experience, resumeUrl.
FR-PROF-2: Applicant can create and update their profile at any time.
FR-PROF-3: Recruiters can view the profile of an applicant who applied to one of their jobs.
FR-PROF-4: Collect only required fields (data minimization).
5.4 Resume Upload (FR-RES)
FR-RES-1: Accept only PDF, DOC and DOCX (validate MIME type and extension).
FR-RES-2: Maximum file size 2 MB; reject larger files with a clear error.
FR-RES-3: Store with a randomized unique filename (never trust the original filename) in server/uploads/resumes/.
FR-RES-4: Save the resume URL on the profile and on the application.
FR-RES-5: Resume files are viewable only by the owning applicant, the recruiter of the job applied to, and admins.
5.5 Applications (FR-APP)
FR-APP-1: Applicant applies to an open job with an optional cover letter; the resume URL is taken from the upload or profile.
FR-APP-2: An applicant cannot apply to the same job twice (unique compound index on job + applicant).
FR-APP-3: Applicant sees all their applications with job title, company/recruiter, applied date and current status.
FR-APP-4: Recruiter sees all applications for each of their jobs, with applicant name, profile details, resume link, cover letter and status.
FR-APP-5: Recruiter can update status among: Applied, Under Review, Shortlisted, Selected, Rejected. Only the job's own recruiter can do this.
FR-APP-6: Applicant may withdraw an application while the status is Applied.
5.6 Admin Controls (FR-ADMIN)
FR-ADMIN-1: List all users with role filter and search; activate or deactivate users; delete users.
FR-ADMIN-2: List all jobs and applications; delete any job.
FR-ADMIN-3: Basic platform counts (total users, jobs, applications) on the admin home page.
5.7 UI and Responsiveness (FR-UI)
Reusable React components styled with Tailwind; consistent look across the app.
Mobile-first responsive layout (navbar collapses to a hamburger menu on small screens).
Loading states, empty states and toast notifications for success and error messages.
Client-side form validation matching server-side validation.

10. Non-Functional Requirements
Security
Passwords hashed with bcrypt; JWT secret from environment variables.
Role-based route protection on both server and client; ownership checks on every job and application mutation.
Input validation on all endpoints (express-validator or Joi); sanitize against NoSQL injection (express-mongo-sanitize).
Use helmet, configure CORS to allow only CLIENT_URL, and add rate limiting on /auth/*.
Resume upload restricted by type and size; randomized filenames; files served only through an authorized route, not as open static files.
Never expose password hashes or stack traces in responses.
Performance and Scalability
Paginate all list endpoints; use .lean() for read queries and index search fields.
Modular layered architecture so services can be split later.
Usability and Compatibility
Responsive on desktop, tablet and mobile; tested on Chrome (recommended), Firefox and Edge.
Data Privacy
Collect only required candidate fields and process them transparently, in line with data-protection principles such as India's DPDP Act 2023.
Maintainability
Consistent code style (ESLint and Prettier), meaningful commit history, README with setup steps.

12. Acceptance Criteria
The project is done when all of these pass:
A user can register, log in and log out as applicant and as recruiter.
Accessing a protected page without a valid token redirects to login; an API call with an invalid or expired token returns 401.
An applicant cannot open recruiter or admin routes (403 on the API, redirect in the UI) and vice versa.
A recruiter can create, edit, close and delete their own job, and cannot modify another recruiter's job.
Applicants can search and filter jobs and view job details.
Applicants can upload a PDF, DOC or DOCX resume under 2 MB; wrong types and oversized files are rejected with a clear message.
An applicant can apply once per job; a duplicate application returns 409; a past-deadline job cannot be applied to.
A recruiter sees applications for their job, opens the resume, and changes status; the applicant sees the new status on their dashboard.
Passwords are stored only as hashes in MongoDB.
Admin can view stats, deactivate a user (who then cannot log in) and delete jobs.
UI is usable at 360 px, 768 px and 1280 px widths.
Every endpoint in section 7 works in Postman with correct status codes.
